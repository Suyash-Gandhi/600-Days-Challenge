# RAM and Memory — From Zero

## First: the one idea you need

Imagine your computer is a desk.

- SSD/HDD = cupboard → stores things permanently.
- RAM = desk → holds things you are currently working with.
- CPU = you → actually does the work.

```text
       SSD
   ┌───────────┐
   │ Programs  │
   │ Photos    │
   │ Files     │
   └─────┬─────┘
         │
       load
         ↓
   ┌───────────┐
   │    RAM    │  ← workspace
   │           │
   │ Program   │
   │ Variables │
   │ Data      │
   └─────┬─────┘
         │
         ↓
       CPU
      does work
```

That's the fundamental idea.

---

# 1. What is RAM?

RAM is the computer's temporary working area.

Suppose you have a program:

```text
Calculator
```

The calculator program is permanently stored on your SSD.

When you open it:

```text
SSD
 │
 │ "Load calculator"
 ↓
RAM
 │
 ↓
CPU
```

The computer puts the necessary parts of the calculator into RAM so the CPU can work with them.

When you close the program, that working memory can be released.

When you turn the computer off, the contents of RAM disappear.

That's why RAM is called volatile memory.

---

# 2. Why can't the CPU just use the SSD?

Because the CPU needs very fast access to the information it is working with.

Think about yourself studying.

You have:

```text
Bookshelf
   ↓
Book
   ↓
Your desk
   ↓
You
```

You don't repeatedly walk to the bookshelf every time you need one sentence.

You put the book on your desk.

Similarly:

```text
SSD → RAM → CPU
```

The SSD is long-term storage.

RAM is the working area.

---

# 3. What actually goes into RAM?

This is the part that matters for cybersecurity.

When a program runs, it needs several things:

```text
Program instructions
Variables
Temporary data
Function information
Dynamic data
```

All of these need memory while the program is running.

For example:

```c
int x = 10;
int y = 20;

int z = x + y;
```

The program needs somewhere to keep:

```text
x = 10
y = 20
z = 30
```

while it runs.

That somewhere is memory.

---

# 4. So what is a memory address?

Now imagine RAM is a huge building with millions/billions of lockers.

Each locker has a number.

```text
Locker       Contents
──────────────────────
1000         25
1001         10
1002         50
1003         99
1004         42
```

The number is the address.

So the CPU can essentially say:

> "Give me whatever is stored at address 1002."

And RAM can provide it.

Computers normally represent these addresses in hexadecimal, so you might see:

```text
0x1000
0x1001
0x7fffffffe000
```

Don't worry about the strange-looking numbers yet.

Just remember:

> Memory address = location of something in memory.

---

# 5. What does "memory" mean?

This is where beginners often get confused.

Memory is a broad term.

RAM is a type of memory.

But when cybersecurity people say:

> "Look at the process's memory"

they are usually talking about the memory being used by a running program.

For example:

```text
Chrome is running
       ↓
Chrome has memory
       ↓
That memory contains:
- code
- variables
- data
- objects
- buffers
- etc.
```

---

# 6. The most important thing: a running program needs memory

Imagine you run:

```text
calculator.exe
```

The executable is sitting on your SSD:

```text
SSD
┌──────────────────┐
│ calculator.exe   │
└──────────────────┘
```

You double-click it.

The OS loads it and creates a process.

Very roughly:

```text
calculator.exe
      ↓
    OS
      ↓
   Process
      ↓
   Memory
      ↓
     CPU
```

So:

> Program on disk ≠ running program

A program on disk is just a file.

A process is that program currently running, with memory and execution state.

This distinction becomes extremely important in cybersecurity.

---

# 7. What does a process's memory look like?

Now imagine the OS gives your running program a workspace.

The workspace contains different areas.

Don't worry about the technical details yet.

Think of it like this:

```text
┌─────────────────────────┐
│ Program instructions    │
│ "What should I do?"     │
├─────────────────────────┤
│ Program data            │
│ "What information?"     │
├─────────────────────────┤
│ Heap                    │
│ "Extra memory I request"│
├─────────────────────────┤
│ Stack                   │
│ "Current function work" │
└─────────────────────────┘
```

These are the four areas you should understand first.

---

# 8. Code / instructions

A program needs instructions.

For example:

```text
add these numbers
compare these values
call this function
open this file
```

Those instructions are represented as machine code in memory.

The CPU reads those instructions and executes them.

```text
Memory
   │
   │ instruction
   ↓
 CPU
   │
   ↓
execute
```

This is extremely important for reverse engineering.

When you open a binary in Ghidra or GDB, you're ultimately dealing with machine instructions that exist in memory when the program runs.

---

# 9. Variables/data

Suppose:

```c
int age = 20;
```

The program needs to store:

```text
20
```

somewhere.

That's memory.

Similarly:

```c
char name[] = "Suyash";
```

The characters need memory.

So a running program's memory contains both:

```text
instructions
+
data
```

---

# 10. Stack — don't overthink it yet

Suppose you have:

```c
void hello() {
    int x = 10;
}
```

When `hello()` runs, the program needs temporary space for things associated with that function.

The stack is one of the places used for this.

Very simplified:

```text
hello()
   ↓
Stack
┌────────────┐
│ x = 10     │
│ other info │
└────────────┘
```

When the function finishes, this temporary function-related information can be removed.

That's the basic idea.

You will later learn that the stack also contains things such as:

- function call information
- saved registers
- return addresses
- local variables

This becomes extremely important for buffer overflow vulnerabilities.

But don't worry about exploitation yet.

---

# 11. Heap — also keep it simple

Sometimes a program doesn't know beforehand how much memory it will need.

It can ask the OS/runtime for memory dynamically.

For example:

```c
int p = malloc(sizeof(int));
```

You can think:

> "Give me some memory that I can use."

The dynamically allocated memory generally comes from the heap.

```text
Program
   │
   │ "I need some memory"
   ↓
 Heap
┌──────────────┐
│ available    │
│ memory       │
└──────────────┘
```

Later:

```c
free(p);
```

means:

> "I'm finished with this memory."

Heap memory becomes extremely important when you study:

- heap overflow
- use-after-free
- double free

But for now, simply remember:

> Stack = mainly function-related temporary memory.  
> Heap = dynamically requested memory.

---

# 12. Now let's put everything together

Suppose this program runs:

```c
int global = 100;

int main() {
    int x = 10;

    int p = malloc(sizeof(int));
    p = 20;
}
```

You can imagine:

```text
              RUNNING PROGRAM
                    │
                    ▼
          ┌──────────────────┐
          │      Memory      │
          │                  │
          │ Code             │
          │ main()           │
          │                  │
          │ Global data      │
          │ global = 100     │
          │                  │
          │ Heap             │
          │ 20               │
          │                  │
          │ Stack            │
          │ x = 10           │
          │ p = address      │
          └──────────────────┘
```

You don't need to memorize exactly where these are located yet.

Just understand what they are for.

---

# 13. Now: why does cybersecurity care?

This is where the topic becomes useful.

Imagine a program has:

```text
Stack
┌──────────────┐
│ return info  │
│ x            │
│ buffer       │
└──────────────┘
```

The programmer expects the buffer to contain:

```text
AAAAAAAAAA
```

But an attacker sends:

```text
AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
```

If the program doesn't properly check the size, the extra data may overwrite other things in memory.

That's a buffer overflow.

So cybersecurity people care about memory because:

> A program's memory contains its data and execution state. If memory is handled incorrectly, attackers may be able to corrupt that state.

That's the connection.

---

# 14. Another cybersecurity example

Imagine a password is temporarily stored in a running program:

```text
Application memory

┌──────────────────────┐
│ username             │
│ "admin"              │
├──────────────────────┤
│ password             │
│ "secret123"          │
├──────────────────────┤
│ application code     │
├──────────────────────┤
│ other data           │
└──────────────────────┘
```

The password might not exist in exactly this form or location in a real application, but the example illustrates the idea.

A memory-analysis tool may inspect the memory of a process.

That's why memory forensics exists.

---

# 15. One more important idea: virtual memory

This was probably one of the things that made my previous answer confusing.

Forget page tables and MMUs for now.

Imagine two programs:

```text
Chrome
Calculator
```

Both programs need memory.

The OS gives each program the illusion that it has its own memory space.

```text
Chrome
┌─────────────────┐
│ its memory      │
└─────────────────┘

Calculator
┌─────────────────┐
│ its memory      │
└─────────────────┘
```

Chrome normally can't simply say:

> "Give me Calculator's memory."

The OS provides memory isolation.

That's one of the fundamental security boundaries in an operating system.

Later you'll learn that this is implemented using virtual memory and address translation.

For now:

> Virtual memory allows each process to have its own protected memory view.

That's enough.

---

# 16. What you actually need to remember right now

Forget the complicated terms from my previous answer.

If you remember these 8 things, you've understood the foundation:

### 1. RAM

Temporary working memory.

### 2. Program vs process

```text
Program = file stored on disk

Process = program currently running
```

### 3. Running programs need memory

Memory holds:

```text
code
data
variables
temporary information
```

### 4. Memory has addresses

```text
0x1000
0x1001
0x1002
```

These identify locations.

### 5. Stack

Mainly used for function-related temporary information.

### 6. Heap

Memory dynamically requested by programs.

### 7. Processes have protected memory

One normal process shouldn't simply access another process's memory.

### 8. Memory bugs can become security vulnerabilities

For example:

```text
Buffer overflow
Use-after-free
Memory corruption
```
