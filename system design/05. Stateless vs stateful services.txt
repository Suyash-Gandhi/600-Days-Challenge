# 5. Stateless vs Stateful Services

## 1. What is a Stateless Service?

A stateless service is a service that does not store information about a client's previous requests between requests. Each request contains the information needed to process it independently.

The service doesn't rely on memory of previous requests to handle the current one.

### Example

Imagine you're using an online shopping website.

You request product details:

`GET /products/101`

The server returns the product information.

Next, you request another product:

`GET /products/102`

The server processes this request independently. It doesn't need to remember that you previously requested product 101.

Real-world examples:
- Product catalog APIs.
- Public weather APIs.
- Image resizing services.
- Services that validate JWT access tokens.
- Microservices that process independent requests.

### How it works

```text
Client
  |
  | Request 1
  v
Server A ───> Response 1
  |
  | Request 2
  v
Server B ───> Response 2
```

Both requests can be handled by different servers because neither server needs to remember the client's previous request.

Key point: Any server instance can process the next request, assuming the required data and configuration are accessible.

---

## 2. What is a Stateful Service?

A stateful service maintains information about a client's previous interactions or the ongoing state of a process.

Its behavior can depend on information retained from earlier requests.

### Example

Imagine you're playing an online multiplayer game.

Your character has:
- 100 health points.
- 50 coins.
- A particular position in the game world.

After you take damage, your health drops to 80.

The game service must maintain or access your updated game state to process future actions correctly.

Real-world examples:
- Multiplayer game servers.
- WebSocket connections that maintain connection-specific state.
- Services managing active workflows.
- Applications that keep user session data in server memory.
- Some database connections and transaction-processing systems.

### How it works

```text
Client
  |
  | Request 1: Start session
  v
Server A
  |
  | Stores session state
  v
Session: {user: 101, cart: [A, B]}
  |
  | Request 2: Continue session
  v
Server A
  |
  | Reads existing state
  v
Response
```

In this example, Server A maintains the session in its memory, so subsequent requests may need to reach the same server.

Key point: Stateful services must preserve or access the state required for future operations.

Important: Stateful does not necessarily mean the data must be stored in server memory. State can also be maintained in a database, Redis, or another external storage system.

---

## 3. Stateless vs Stateful: Key Differences

| Feature | Stateless Service | Stateful Service |
|---|---|---|
| Definition | Processes requests without relying on previously retained client state | Maintains or relies on state across operations |
| Request independence | Requests can generally be processed independently | Requests may depend on previous operations |
| State storage | No required per-client state inside the service between requests | State must be maintained or accessible somewhere |
| Server dependency | Requests can usually go to any healthy instance | May require access to specific state or a particular instance |
| Horizontal scaling | Generally easier | Can be more complex |
| Load balancing | Usually straightforward | May require shared state or session affinity |
| Failure recovery | Often simpler if requests are repeatable | May require state recovery or reconnection |
| Server memory usage | No persistent per-client state is required | May retain client or process state in memory |
| Example | Product catalog API | In-memory session service |

### The most important distinction

Stateless doesn't mean the application has no data.

A stateless API can read and write to a database. It simply doesn't depend on retaining a client's previous request state inside the service instance.

Similarly, a stateful service doesn't necessarily store all its state locally. It may use an external database or distributed state store.

## 4. Understanding Through a Real-World Example

Consider an e-commerce application.

### A. Stateless: Product Search

You search for a product.

```http
GET /api/products?search=laptop
```

The server queries the database and returns matching products.

The next request might go to another server without affecting the result.

```text
                Load Balancer
                /           \
           Server A       Server B
                \           /
                  Database
```

Both servers can independently process product searches.

If Server A fails, Server B can continue handling requests, assuming the shared dependencies remain available.

### B. Stateful: Shopping Cart

Suppose your shopping cart exists only in Server A's memory.

```text
Client ───> Server A
               |
               v
       Cart stored in memory
       [Laptop, Mouse]
```

Now imagine the next request goes to Server B.

```text
Client ───> Server B
               |
               v
        Cart not found!
```

Server B cannot find the cart because the state exists only in Server A's memory.

This creates a problem when scaling or recovering from failures.

### C. How to solve the shopping cart problem

Store the cart in a shared database or distributed cache.

```text
                 Load Balancer
                 /           \
            Server A       Server B
                 \           /
                  Redis
                   |
              Shopping Cart
```

Now both servers can access the same cart.

Important architectural insight: The application can be stateful from the user's perspective while its API servers remain stateless.

This is a common design approach in modern web applications.

## 5. Why Stateless Services Are Easier to Scale

Suppose your application receives 10,000 requests per second.

One server cannot handle the entire workload, so you add more servers.

### With stateless services

```text
                   Load Balancer
                 /       |       \
                /        |        \
           Server A  Server B  Server C
                \        |        /
                 Shared Database
```

Requests can be distributed across healthy servers.

When traffic increases, you can add more instances.

For example:

- 1 server handles 1,000 requests/second.
- 5 servers might handle approximately 5,000 requests/second.
- 10 servers might handle approximately 10,000 requests/second.

These numbers are illustrative; actual capacity depends on workload, bottlenecks, and infrastructure.

### With stateful services

Scaling can be more complicated because each instance may hold different pieces of state.

For example:

```text
Client A ───> Server A ───> Session A
Client B ───> Server B ───> Session B
Client C ───> Server C ───> Session C
```

If a client must return to the same server, you may need sticky sessions, also called session affinity.

However, sticky sessions introduce limitations:
- Requests may become unevenly distributed.
- A failed server may cause session loss.
- Scaling and deployments become more complicated.

A shared session store can reduce these problems.

Remember: Stateful services can also scale horizontally. They simply require more careful state management and coordination.

## 6. Stateless vs Stateful Authentication

Authentication is a common interview topic where this distinction matters.

### A. Stateless authentication using JWT

A user logs in and receives a signed access token.

For subsequent requests:

```text
Client
  |
  | Request + JWT
  v
Server A
  |
  | Validate JWT signature and claims
  v
Response
```

Another request can go to Server B, which validates the same token independently.

The server doesn't need to retrieve a session record for every request, provided the token contains the required claims and the system's validation rules permit this.

Advantages:
- Easier horizontal scaling.
- No mandatory server-side session lookup for every request.
- Works well with distributed APIs.

Disadvantages:
- Revoking a token before expiration can be difficult without additional mechanisms.
- Tokens can become stale.
- Token expiration, key rotation, and secure storage require careful handling.

JWT-based authentication is not automatically stateless in every implementation. For example, a system may maintain a server-side token revocation list.

### B. Stateful authentication using sessions

A user logs in and receives a session identifier in a cookie.

```text
Client
  |
  | Session ID
  v
Server
  |
  | Look up session
  v
Session Store
  |
  v
Authenticated User
```

The session store maintains information about the authenticated user.

Advantages:
- Sessions can be invalidated centrally.
- Server-side authentication state can be updated.
- Session expiration and management can be straightforward.

Disadvantages:
- Session storage must remain available.
- Distributed deployments need shared session storage or another session-management strategy.
- Session lookups add operational complexity.

### Quick comparison

| Feature | JWT-based approach | Session-based approach |
|---|---|---|
| Typical state model | Can be stateless | Stateful |
| Client stores | Access token | Session identifier |
| Server-side session lookup | Not necessarily required | Typically required |
| Centralized session revocation | Requires additional mechanisms or short token lifetimes | Usually straightforward |
| Horizontal scaling | Generally straightforward | Straightforward with shared session storage |

Neither approach is universally better. The right choice depends on security requirements, revocation needs, application architecture, and operational constraints.

## 7. Stateless vs Stateful in System Design

Understanding this distinction helps you make better architectural decisions.

### When should you choose stateless services?

Stateless services are especially useful when:
- You expect unpredictable traffic.
- You need easy horizontal scaling.
- You are building REST APIs or microservices.
- You want straightforward server replacement and recovery.
- You want to distribute requests across multiple instances.

Examples:
- Product search APIs.
- Public content APIs.
- Image-processing APIs.
- Stateless authorization checks.

### When should you choose stateful services?

Stateful services are useful when:
- The system must maintain an ongoing interaction.
- Operations depend on previous actions.
- A persistent connection or process context is needed.
- Maintaining the current state is central to the service's function.

Examples:
- Multiplayer game servers.
- Live collaboration services.
- Long-running workflow engines.
- Real-time communication systems.

### A practical design principle

A common architecture is to keep application servers as stateless as practical and move durable or shared state into suitable storage systems.

For example:

```text
                 Web / Mobile Client
                         |
                         v
                    Load Balancer
                         |
               +---------+---------+
               |                   |
               v                   v
          API Server A        API Server B
               |                   |
               +---------+---------+
                         |
              +----------+----------+
              |                     |
              v                     v
           Database                Redis
        (durable data)      (cache/session data)
```

Here:
- API servers process requests without depending on local session memory.
- The database stores durable application data.
- Redis can store sessions, cached results, or temporary shared state.

Redis and similar systems are optional design choices, not requirements for every application.

## 8. Cybersecurity Relevance

The stateless/stateful distinction affects authentication, session security, and availability.

### A. Session hijacking

In a stateful session system, an attacker who steals a valid session identifier may impersonate the user.

Mitigations:
- Use HTTPS.
- Set appropriate `Secure`, `HttpOnly`, and `SameSite` cookie attributes.
- Rotate session identifiers after authentication or privilege changes.
- Apply expiration and server-side invalidation.

### B. JWT security

A JWT is generally signed, not encrypted by default. Its payload may be readable by anyone who obtains it.

Mitigations:
- Validate signatures and relevant claims.
- Enforce expiration and issuer/audience checks as appropriate.
- Use secure transport and storage.
- Plan token revocation and key rotation.
- Never treat a decoded token as trustworthy until its signature and claims are validated.

### C. Denial-of-service risks

Stateful services may consume memory or other resources for each active session or connection.

An attacker could exploit this by creating excessive sessions or connections.

Mitigations:
- Apply connection and request limits.
- Use rate limiting.
- Set session expiration and resource quotas.
- Monitor memory, connection counts, and unusual traffic.
- Apply backpressure and admission controls.

### D. Availability and failure handling

If a service stores essential state only in local memory, a server crash may destroy that state.

For critical state, use suitable persistence, replication, recovery, or checkpointing strategies.

Cybersecurity takeaway: Stateless architecture can simplify scaling and recovery, but it does not automatically make a service secure. Authentication, authorization, validation, and resource protection remain necessary.

## 9. Full-Stack Development Relevance

This concept directly affects frontend behavior, backend APIs, and data storage.

### Frontend

A frontend may maintain temporary state such as:
- Form inputs.
- Selected filters.
- Open tabs.
- UI preferences.

For example, React's `useState` maintains component state while the component is mounted. That state is not automatically shared across servers or persisted after a page reload.

### Backend

Backend developers decide how requests are processed and where application state is stored.

For example, an Express.js API can authenticate a request using a JWT without storing a server-side session, or it can use session middleware backed by a shared session store.

### Database

The database can preserve information independently of the API server handling the request.

For example:

```text
React Frontend
      |
      v
Node.js / Express API
      |
      v
PostgreSQL Database
```

A user can send requests to different API instances, and each instance can access the same persistent user and order records.

### Practical full-stack example

Consider a MERN-style application:

- React: Maintains temporary interface state.
- Node.js/Express: Handles API requests.
- MongoDB: Stores durable application data.
- Redis (optional): Stores sessions, cached data, or temporary shared state.

The backend can be designed to be stateless between requests even though the overall application stores substantial amounts of data.

Full-stack takeaway: Learn to distinguish UI state, server-side session state, and persistent database state. They serve different purposes.

## 10. Common Interview Questions

### Q1. What is the main difference between stateless and stateful services?

A stateless service processes requests without relying on retained client state between requests. A stateful service maintains or relies on state across operations.

### Q2. Why are stateless services easier to scale?

Any healthy server instance can generally handle a request without needing access to state stored exclusively on another instance. This makes load balancing and adding or removing instances easier.

### Q3. Can a stateless service use a database?

Yes. Statelessness refers to how the service manages state between requests, not whether it accesses persistent storage.

### Q4. Is a JWT-based API always stateless?

No. An API may use JWTs while also maintaining server-side sessions, revocation lists, or other state. Statelessness depends on the complete implementation.

### Q5. Can stateful services scale horizontally?

Yes. They can use shared state stores, replication, partitioning, session affinity, or specialized coordination mechanisms.

### Q6. What are sticky sessions?

Sticky sessions, or session affinity, direct a client's requests to the same server instance. They can help when session data exists only in local memory, but they can complicate load balancing and failover.

### Q7. Is Redis stateful or stateless?

Redis is a stateful data store because it maintains data between operations. An application that uses Redis can nevertheless keep its API servers stateless.

### Q8. Is a REST API stateless?

REST's stateless constraint requires each request to contain the information needed to understand it, without depending on stored client session context on the server. A REST API can still access databases and other persistent resources.

## 11. Quick Revision Notes

Remember these five points:

1. Stateless: The service does not rely on retaining client state between requests.
2. Stateful: The service maintains or relies on state across operations.
3. Scalability: Stateless services are generally easier to scale horizontally.
4. Shared state: Databases and distributed caches allow multiple server instances to access common data.
5. Real-world architecture: An application can maintain user sessions and persistent data while keeping its API servers stateless.

### One-line interview answer

> A stateless service processes each request independently without relying on previously retained client state, making horizontal scaling easier, whereas a stateful service maintains or relies on information across requests. Stateful systems can also scale horizontally when their state is managed appropriately.
