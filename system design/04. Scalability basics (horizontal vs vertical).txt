# 4. Scalability Basics (Horizontal vs Vertical Scaling)

## 1. What is Scalability?

Scalability is a system's ability to handle increasing workloads by adding resources without significantly degrading performance.

As the number of users, requests, and amount of data increases, a scalable system can adapt to that growth.

### Example

Imagine you're building an e-commerce application.

- Initially, your application handles 100 users.
- As your business grows, it handles 10,000 users.
- Eventually, it needs to support 1 million users.

If your application can accommodate this growth by adding resources or distributing workloads efficiently, it is scalable.

The two primary approaches to scaling are:
1. Vertical scaling (Scaling Up)
2. Horizontal scaling (Scaling Out)

---

## 2. Vertical Scaling (Scaling Up)

Vertical scaling means increasing the resources of a single server to handle more workload.

You upgrade the existing machine rather than adding more machines.

### Example

Suppose your application runs on a server with:
- 4 CPU cores
- 8 GB RAM
- 100 GB storage

As traffic increases, you upgrade the server to:
- 16 CPU cores
- 64 GB RAM
- 1 TB storage

Your application continues running on the same server, but that server now has more resources.

### Architecture

```text
       Users
         |
         v
  +------------------+
  | Application      |
  | Server           |
  |                  |
  | Before:          |
  | 4 CPU / 8 GB RAM |
  |                  |
  | After:           |
  | 16 CPU / 64 GB   |
  +------------------+
```

### Advantages
- Simple to implement.
- Requires fewer architectural changes.
- Easier to manage because there are fewer servers.
- Can improve performance quickly.

### Disadvantages
- Hardware has an upper limit.
- Powerful servers can become expensive.
- A single server can become a single point of failure.
- Upgrading may require downtime, depending on the infrastructure.

### Real-world example

A database server initially has 8 GB of RAM. As the database grows, you upgrade it to 64 GB of RAM and use a faster CPU.

This is vertical scaling.

Key idea: Make one machine more powerful.

---

## 3. Horizontal Scaling (Scaling Out)

Horizontal scaling means adding more servers or machines to distribute the workload.

Instead of making one server more powerful, you add multiple servers and distribute incoming requests among them.

### Example

Suppose your application initially runs on one server.

As traffic grows, you add two more servers.

Now, three servers can handle requests instead of one.

### Architecture

```text
                 Users
                   |
                   v
           +----------------+
           | Load Balancer  |
           +----------------+
              /     |     \
             /      |      \
            v       v       v
       +--------+ +--------+ +--------+
       | Server | | Server | | Server |
       |   1    | |   2    | |   3    |
       +--------+ +--------+ +--------+
```

The load balancer distributes incoming requests across available servers.

If one server becomes overloaded, the load balancer can send requests to other healthy servers, assuming they have sufficient capacity.

### Advantages
- Can support substantial growth by adding servers.
- Provides opportunities for high availability and fault tolerance.
- Allows workloads to be distributed.
- Individual servers can often be upgraded or replaced independently.
- Can scale capacity incrementally.

### Disadvantages
- More complex architecture.
- Requires coordination between multiple servers.
- May introduce network communication overhead.
- Shared state, sessions, and data consistency can be challenging.
- Load balancing and monitoring require additional infrastructure.

### Real-world example

A video-streaming application experiences a huge increase in viewers.

Instead of upgrading one server indefinitely, the company deploys additional application servers behind load balancers.

This is horizontal scaling.

Key idea: Add more machines to share the workload.

---

## 4. Horizontal vs. Vertical Scaling

| Feature | Vertical Scaling | Horizontal Scaling |
|---|---|---|
| Also called | Scaling up | Scaling out |
| Approach | Increase resources on one machine | Add more machines |
| Architecture | Usually simpler | Usually more complex |
| Maximum capacity | Limited by machine capabilities | Can grow by adding machines, within system limits |
| Fault tolerance | One server may be a single point of failure | Can improve resilience with redundancy |
| Downtime | Upgrades may require downtime | Can often add servers without downtime |
| Cost | Powerful hardware can be expensive | More servers and coordination can increase costs |
| Load distribution | Usually unnecessary across machines | Often uses a load balancer or distributed processing |
| Best suited for | Workloads that benefit from a larger machine | Workloads that can be distributed across machines |
| Example | Upgrade a server from 8 GB to 64 GB RAM | Add three application servers instead of one |

Important: Horizontal scaling does not automatically guarantee high availability. The application, load balancer, database, network, and other dependencies must also be designed to avoid single points of failure.

## 5. How Does a System Scale in Practice?

Consider a full-stack web application with the following architecture:

```text
                  Users
                    |
                    v
              +-----------+
              | Frontend  |
              +-----------+
                    |
                    v
              +-----------+
              |   Load    |
              |  Balancer |
              +-----------+
                 /     \
                v       v
          +---------+ +---------+
          | Backend | | Backend |
          | Server 1| | Server 2|
          +---------+ +---------+
                \       /
                 \     /
                  v   v
              +-----------+
              |  Database |
              +-----------+
```

Initially, you might have one frontend deployment, one backend server, and one database server.

As traffic grows, you can scale different components independently.

### Step 1: Scale the backend horizontally

Add more backend instances and distribute incoming requests across them.

This works best when application servers are stateless or when shared state is stored in a suitable external system.

### Step 2: Scale the database vertically

Upgrade the database server's CPU, RAM, or storage to handle heavier queries and larger datasets.

This can be a practical first step, but it has hardware and cost limits.

### Step 3: Scale database reads

If read traffic becomes a bottleneck, introduce read replicas.

```text
           Backend Servers
                  |
                  v
            +-----------+
            | Primary DB|
            +-----------+
                  |
             Replication
              /       \
             v         v
       +----------+ +----------+
       | Read     | | Read     |
       | Replica 1| | Replica 2|
       +----------+ +----------+
```

Read-heavy workloads can send suitable queries to replicas while writes go to the primary database.

However, replication lag and consistency requirements must be considered.

### Step 4: Introduce caching

Use a cache such as Redis to store frequently accessed data.

```text
User Request
     |
     v
   Backend
     |
     v
    Cache
     |
     | Cache miss
     v
  Database
```

A cache hit can avoid a database query entirely, reducing latency and database load.

### Step 5: Scale additional components when necessary

Depending on the bottleneck, you might also introduce:
- A content delivery network (CDN) for static assets.
- Message queues for asynchronous tasks.
- Database sharding to distribute data across multiple database nodes.
- Auto-scaling to adjust server capacity based on demand.

The important principle is to identify the bottleneck before scaling. Adding application servers will not solve every problem if the database is already overloaded.

## 6. When Should You Use Horizontal or Vertical Scaling?

### Use vertical scaling when:
- Your application is relatively small.
- You want a straightforward infrastructure.
- A workload benefits from more CPU or RAM on one machine.
- Your database or software has limited support for distribution.
- You need a quick capacity upgrade.

### Use horizontal scaling when:
- Traffic is growing substantially.
- Your application can distribute requests across servers.
- You need greater resilience through redundancy.
- You want to add capacity incrementally.
- Your infrastructure supports distributed workloads.

### Can you use both?

Yes. Real-world systems commonly use a combination of horizontal and vertical scaling.

For example:
- Increase the RAM of each database server through vertical scaling.
- Add backend instances through horizontal scaling.
- Add read replicas to distribute database reads.
- Cache frequently accessed data to reduce total workload.

The right approach depends on workload characteristics, bottlenecks, cost, and reliability requirements.

## 7. Important System Design Concepts Related to Scalability

### A. Stateless vs. Stateful Applications

A stateless application server does not depend on locally stored session state to process each request.

For example, multiple backend servers can validate a session using a shared session store or an appropriately designed token-based authentication mechanism.

Stateless servers are generally easier to scale horizontally because requests can be routed to different instances.

A stateful application may require session affinity, shared storage, or other coordination mechanisms.

### B. Load Balancing

A load balancer distributes requests across multiple servers.

Common strategies include:
- Round robin.
- Least connections.
- Weighted routing.
- Routing based on server health.

Load balancing helps distribute traffic, but the routing strategy should match the workload and infrastructure.

### C. Bottlenecks

A bottleneck is a component that limits the performance of the overall system.

For example:

```text
100,000 incoming requests
          |
          v
    10 Backend Servers
          |
          v
   Database overloaded
          |
          v
   Slow application
```

Even if you add more backend servers, the application may remain slow because all those servers depend on the same overloaded database.

Scaling requires addressing the actual bottleneck, not simply adding resources everywhere.

### D. Auto-Scaling

Auto-scaling automatically adjusts the number of running instances according to demand or configured metrics.

For example:
- Low traffic → 2 servers.
- Moderate traffic → 5 servers.
- High traffic → 10 servers.

Auto-scaling can help manage changing workloads and infrastructure costs, but it requires appropriate thresholds, capacity limits, and startup-time considerations.

## 8. Cybersecurity Relevance

Scalability decisions can affect the security and availability of a system.

### Horizontal scaling
- More server instances require consistent security configurations and patching.
- Load balancers should distribute traffic only to healthy, authorized backend instances.
- Authentication and authorization must work consistently across all instances.
- Rate limiting should be coordinated appropriately so attackers cannot bypass limits by distributing requests across servers.
- Auto-scaling policies must be protected against abuse that could cause excessive infrastructure costs.

### Vertical scaling
- A more powerful server is not inherently more secure.
- A single-server architecture can create a significant availability risk if that server fails or is attacked.
- Resource exhaustion can still occur, even with powerful hardware.
- Resource limits, monitoring, access controls, and secure configuration remain essential.

### Example: Denial-of-service attacks

An attacker sends a massive number of requests to an application.

Horizontal scaling might increase capacity, but uncontrolled auto-scaling could also increase infrastructure costs without stopping the attack.

Defenses can include rate limiting, web application firewalls, traffic filtering, caching, and appropriate scaling limits.

Security takeaway: Scalability improves a system's ability to handle workload growth, but it must be combined with security controls to protect availability and prevent resource abuse.

## 9. Full-Stack Development Relevance

Scalability is important across the entire full-stack application.

| Layer | Scaling techniques | Example |
|---|---|---|
| Frontend | CDN, static asset caching | Serve JavaScript and images from a CDN |
| Backend | Horizontal scaling, load balancing | Run multiple Node.js or Java API instances |
| Database | Vertical scaling, read replicas, sharding | Distribute database workload |
| Caching | Application or distributed caching | Store frequently requested product data in Redis |
| Background processing | Message queues, worker pools | Process emails and reports asynchronously |
| Infrastructure | Auto-scaling, orchestration | Adjust application replicas based on demand |

### Example: Scaling a full-stack e-commerce application

Suppose you build an online store using React, Node.js, and PostgreSQL.

Initially:
- React serves the frontend.
- One Node.js server handles API requests.
- PostgreSQL stores product and order information.

As the number of users grows:
1. Serve frontend assets through a CDN.
2. Run multiple Node.js instances behind a load balancer.
3. Cache frequently accessed product information.
4. Optimize slow SQL queries and add appropriate indexes.
5. Introduce database read replicas if read traffic warrants them.
6. Use a message queue for tasks such as sending order confirmation emails.

This allows individual components to scale according to their own requirements.

## 10. Common Interview Questions

Q1. What is the difference between horizontal and vertical scaling?

Vertical scaling increases the resources of an existing machine, whereas horizontal scaling adds more machines to distribute the workload.

Q2. Which approach is better?

Neither is universally better. Vertical scaling is usually simpler, while horizontal scaling can support distributed workloads and improve resilience when designed appropriately.

Q3. Why is horizontal scaling often preferred for large web applications?

Web applications can often distribute independent requests across multiple servers, allowing capacity to grow by adding instances. It can also support redundancy and fault tolerance.

Q4. Does adding more servers always improve performance?

No. A shared database, network, cache, or other component might become the bottleneck. Additional servers can also introduce coordination overhead.

Q5. Can a database scale horizontally?

Yes. Techniques include read replicas, partitioning, and sharding. Each has different trade-offs involving consistency, complexity, and workload distribution.

Q6. What is the relationship between scalability and availability?

Scalability concerns handling increasing workload. Availability concerns whether a system remains accessible. Horizontal scaling can improve availability when redundancy, health checks, and failover are properly implemented, but the two concepts are not identical.

Q7. What is the difference between scaling up and scaling out?

- Scaling up = vertical scaling.
- Scaling out = horizontal scaling.

Q8. What is a common mistake when scaling an application?

Adding more application servers without investigating whether the database or another dependency is already the limiting factor.

## 11. Quick Revision Notes

Remember these key points:

- Scalability: The ability to handle increasing workload by adding resources.
- Vertical scaling: Make an existing machine more powerful.
- Horizontal scaling: Add more machines.
- Load balancer: Distributes requests across multiple servers.
- Stateless application: Easier to scale horizontally because requests do not depend on local session state.
- Database read replica: Helps distribute suitable read workloads.
- Caching: Reduces repeated work and pressure on downstream systems.
- Auto-scaling: Adjusts infrastructure capacity according to demand.
- Bottleneck: The component limiting overall system performance.

### One-line interview answer

Scalability is a system's ability to handle increasing workloads. Vertical scaling increases the resources of an existing machine, while horizontal scaling adds more machines to distribute the workload. Modern web applications often combine both approaches with caching, load balancing, and database optimization.
